Praca w zespole

Zespół

  • 3 osoby, jedno repozytorium na GitHubie: fork wkoszela/WdTB-2026-Backend--projectname-- przemianowany na WdTB-2026-Backend-<nazwaprojektu> (krok po kroku: LAB 01).
  • Jedna osoba wpisuje zespół do arkusza zespołów w zakładce swojej grupy: imię i nazwisko, numer indeksu, e-mail każdej osoby, link do repozytorium i krótki opis projektu (1–2 zdania). Repozytorium hostuje jedna osoba z zespołu. Bez wpisu w arkuszu zespół nie jest oceniany.
  • Osoba hostująca repozytorium jest jego właścicielem. Pozostałe osoby dodaje jako współpracowników (Settings → Collaborators → Add people). Prowadzącego nie trzeba dodawać: repozytorium jest publiczne, wystarczy link w arkuszu.

Kto co robi

Nie ma przydzielonych ról. Pracujecie razem nad całym projektem i dzielicie pracę na zajęciach, np. według tabel czy funkcji.

Na zajęciach pracujecie na jednym laptopie osoby hostującej.

Przepływ pracy

Git → Pull  →  zmiany w kodzie  →  Git → Commit  →  Push  →  zielone „Testy i reguły”
  1. Pull przed rozpoczęciem pracy: pobieracie zmiany pozostałych osób z zespołu.
  2. Commit z krótkim opisem, co zmienia, np. „Encja rezerwacji i dane startowe”.
  3. Push bezpośrednio na main. Wynik sprawdzenia: zakładka Actions, przebieg „Testy i reguły”.

Konflikty w Gicie

  • Każda osoba ma własne pliki. Dzielicie pracę po tabelach lub funkcjach; klasy innej osoby zmieniacie po uzgodnieniu z nią.
  • data.sql edytuje cały zespół, więc konflikty są tu najczęstsze. Jedna osoba dopisuje najpierw nagłówki sekcji (-- ===== tabela (osoba) =====) dla wszystkich tabel i wysyła je jednym commitem; potem każda osoba wypełnia tylko swoje sekcje (szczegóły: LAB 02, krok C3).
  • Nowe materiały z szablonu pobiera osoba hostująca przyciskiem Sync fork → Update branch na GitHubie, a reszta robi Git → Pull. Przy konflikcie nie klikajcie Discard commits; zgłoście go prowadzącemu.
  • Przed Push zróbcie Git → Pull. Jeśli IntelliJ pokaże konflikt, rozwiążcie go razem (Merge…) i dopiero wtedy wyślijcie zmiany.

Zrozumienie projektu

  • Pracujecie nad projektem razem, więc każda osoba powinna wiedzieć, jak działa cały projekt, a nie tylko swoja część.
  • Na ocenie prowadzący może poprosić dowolną osobę z zespołu o wyjaśnienie fragmentu kodu albo o drobną zmianę.
  • Raport Wkład członków zespołu (zakładka Actions → Summary) pokazuje commity per autor od poprzedniego tagu. To punkt wyjścia do rozmowy, nie ocena.

Kiedy zespół się sypie

Jeśli ktoś nie pracuje, zespół zgłasza to prowadzącemu od razu, na zajęciach. Nie ratujcie oceny kolegi własną pracą bez słowa.
