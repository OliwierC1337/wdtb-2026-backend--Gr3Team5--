TeoriaB · Wprowadzenie: encje, typy kolumn, @Embeddable

B1. Encja to klasa, która opisuje tabelę

Na LAB 01 widzieliście w oknie Run polecenie create table user_account. Hibernate wygenerował je z klasy UserAccount. Tak działa JPA: klasa ↔ tabela, pole ↔ kolumna, obiekt ↔ wiersz. Otwórzcie account/domain/UserAccount.java i porównajcie z tabelą w konsoli H2:

Adnotacja Znaczenie W UserAccount
@Entity klasa jest encją: Hibernate tworzy dla niej tabelę nad klasą
@Table(name = "…") nazwa tabeli w bazie (małe litery, podkreślenia) user_account
@Id + @GeneratedValue(strategy = IDENTITY) klucz główny; numer nadaje baza (1, 2, 3…) Long id
@Column(name, nullable, unique, length) nazwa i ograniczenia kolumny email: wymagany, unikalny, 120 znaków
@Enumerated(EnumType.STRING) enum zapisany jako tekst ('ADMIN'), a nie numer pozycji AccountRole role
konstruktor protected bez argumentów wymaga go Hibernate; drugi, publiczny, służy Wam protected UserAccount() {}

B2. Typy kolumn

Dane Typ pola w Javie Uwagi
tekst String zawsze z length, np. 60 lub 120
liczby całkowite, ilości Integer, Long liczba miejsc, sztuk, punktów
kwoty, ceny, oceny dziesiętne BigDecimal nigdy double ani float: 0.1 + 0.2 daje 0.30000000000000004; kolumna precision = 10, scale = 2
data, data z godziną LocalDate, LocalDateTime w data.sql: '2026-11-14', '2026-11-14 18:00:00'
status, typ, kategoria ze stałej listy enum zawsze z @Enumerated(EnumType.STRING)
tak / nie Boolean np. active

B3. Przykład: trzy encje kawiarni

Tak wyglądają trzy tabele bez relacji dla kawiarni z LAB 01. To wzór: Wy w części E tworzycie tabele ze swojego projektu. Każda encja leży w pakiecie swojego modułu: seating.entity, menu.entity, guest.entity.

Stolik, klasa CafeTable (nazwa Table jest zajęta przez adnotację JPA):

package pl.wsb.kawiarnia.seating.entity;

import jakarta.persistence.*;

@Entity
@Table(name = "cafe_table")
public class CafeTable {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "number", nullable = false, unique = true)
    private Integer number;

    @Column(name = "seats", nullable = false)
    private Integer seats;

    @Column(name = "room", nullable = false, length = 40)
    private String room;

    @Column(name = "active", nullable = false)
    private Boolean active;                  // stolik w użyciu

    protected CafeTable() {
    }

    public CafeTable(Integer number, Integer seats, String room, Boolean active) {
        this.number = number;
        this.seats = seats;
        this.room = room;
        this.active = active;
    }

    // gettery: Code → Generate… → Getter → zaznaczcie wszystkie pola
}

Hibernate generuje z tej klasy:

create table cafe_table (
    active boolean not null,
    number integer not null unique,
    seats integer not null,
    id bigint generated by default as identity,
    room varchar(40) not null,
    primary key (id)
)

Pozycja menu ma kategorię ze stałej listy (enum) i cenę (kwota). Najpierw enum MenuCategory:

package pl.wsb.kawiarnia.menu.entity;

public enum MenuCategory {
    COFFEE, TEA, CAKE
}

Potem encja MenuItem:

@Entity
@Table(name = "menu_item")
public class MenuItem {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "name", nullable = false, unique = true, length = 60)
    private String name;

    @Enumerated(EnumType.STRING)
    @Column(name = "category", nullable = false, length = 20)
    private MenuCategory category;

    @Column(name = "price", nullable = false, precision = 10, scale = 2)
    private BigDecimal price;

    @Column(name = "available", nullable = false)
    private Boolean available;

    protected MenuItem() {
    }

    // konstruktor z polami i gettery: Code → Generate…
}

W logu enum jest tekstem, a cena liczbą z dwoma miejscami po przecinku. Z double byłoby float(53), czyli zaokrąglenia przy każdym dodawaniu:

create table menu_item (
    available boolean not null,
    price numeric(10,2) not null,
    id bigint generated by default as identity,
    name varchar(60) not null unique,
    category enum ('CAKE','COFFEE','TEA') not null,
    primary key (id)
)

Gość, klasa Guest, ma datę i kolumnę opcjonalną: telefon nie jest wymagany, więc nie ma nullable = false. Adres to osobna klasa wbudowana, opisana w B4:

@Entity
@Table(name = "guest")
public class Guest {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "full_name", nullable = false, length = 80)
    private String fullName;

    @Column(name = "phone", length = 20)
    private String phone;

    @Column(name = "registered_on", nullable = false)
    private LocalDate registeredOn;

    @Embedded
    private Address address;               // klasa wbudowana z B4

    protected Guest() {
    }

    // konstruktor z polami i gettery: Code → Generate…
}

B4. Klasa wbudowana: @Embeddable

Czasem kilka kolumn tworzy całość, np. adres: ulica, miasto, kod pocztowy. Zamiast trzech luźnych pól w encji tworzy się małą klasę z @Embeddable i używa jej w encji jako pola z @Embedded. Klasa wbudowana nie jest osobną tabelą: jej kolumny trafiają do tabeli encji, która jej używa.

@Embeddable
public class Address {

    @Column(name = "street", length = 80)
    private String street;

    @Column(name = "city", length = 40)
    private String city;

    @Column(name = "postal_code", length = 6)
    private String postalCode;

    protected Address() {
    }
}

W encji Guest wystarczy pole @Embedded private Address address;. Hibernate tworzy jedną tabelę guest, w której są też kolumny adresu:

create table guest (
    registered_on date not null,
    postal_code varchar(6),
    id bigint generated by default as identity,
    phone varchar(20),
    city varchar(40),
    full_name varchar(80) not null,
    street varchar(80),
    primary key (id)
)
@Entity @Embeddable
własna tabela tak nie, kolumny w tabeli encji
własne id tak nie
przykłady stolik, produkt, klient adres, okres od–do, kwota z walutą, dane kontaktowe

Klasa @Embeddable leży w tym samym pakiecie <moduł>.entity co encja (R2.02). Nie liczy się jako jedna z 3 tabel, ale jej kolumny liczą się do kolumn tabeli encji (R2.04). Na ocenę 5 co najmniej jedna encja ma pole @Embedded (R2.07).

ZadanieD · Wybór tabel

Na podstawie tematu Waszego projektu sami wybierzcie 3 tabele. Jeśli któraś tabela powinna wskazywać na inną (np. rezerwacja na stolik), na razie nie budujcie relacji: pomińcie kolumnę klucza obcego, dojdzie na kolejnych zajęciach. Dla każdej tabeli ustalcie:

Na ocenę 5 dodatkowo: w co najmniej jednej tabeli kolumna typu enum z @Enumerated(EnumType.STRING), np. status albo kategoria (R2.06), i w co najmniej jednej tabeli klasa wbudowana @Embeddable, np. adres albo okres od–do (R2.07). Wzór w częściach B3 i B4.

ZadanieE · Encje Waszego projektu

Tworzycie własne 3 tabele z części D. Wzorem są encje kawiarni z części B3. Nazwy klas, pól i pakietów po angielsku, jak w UserAccount. Pracujecie razem całym zespołem (C3).

E1. Pakiety modułów

Prawy przycisk na pakiecie pl.wsb.<projekt> → New → Package → wpiszcie <moduł>.entity, np. menu.entity (IntelliJ utworzy oba poziomy). Tak samo dla pozostałych modułów z części D (R2.02). Gotowa klasa UserAccount zostaje w account.domain.

ZadanieF · Dane startowe i konsola H2

F1. Przykładowe dane: insert w data.sql

Hibernate tworzy tabele od nowa przy każdym starcie, a potem Spring Boot wykonuje src/main/resources/data.sql. Do każdej Waszej tabeli dopiszcie polecenie insert z co najmniej 3 przykładowymi wierszami, w sekcji tej tabeli (C3) na końcu pliku, pod kontami z LAB 01. Wzór jest w części B3. Zasady:

  • Bez id: baza numeruje wiersze sama, od 1.
  • Nazwy kolumn dokładnie jak w @Column(name); enumy jako tekst w apostrofach (np. 'COFFEE'); daty jako '2026-10-01'; kwoty z kropką (9.00).
  • Dane sensowne dla Waszego tematu, nie „test1”, „test2”. Reguła R2.03 sprawdza, że każda tabela ma co najmniej 3 wiersze.
-- ===== LAB 02 · <nazwa_tabeli> =====
insert into <nazwa_tabeli> (<kolumna1>, <kolumna2>, <kolumna3>) values
    (…, …, …),
    (…, …, …),
    (…, …, …);

F2. Sprawdzenie w konsoli H2

Po Rerun otwórzcie http://localhost:8080/h2-console (JDBC URL jdbc:h2:file:./data/wdtb, użytkownik sa, hasło puste). Po lewej stronie jest lista tabel: rozwińcie każdą swoją tabelę i sprawdźcie kolumny. Potem dla każdej tabeli wykonajcie select i porównajcie wiersze z data.sql:

select * from <nazwa_tabeli>;

Na przykładzie kawiarni: select * from menu_item; albo z warunkiem select name, price from menu_item where category = 'COFFEE' order by price;

Każda tabela ma pokazać tyle wierszy, ile wpisaliście. Pusta tabela oznacza brak sekcji w data.sql albo literówkę w nazwie tabeli.

F3. Typowe błędy przy starcie

Komunikat w logu Przyczyna i poprawka
Column "…" not found nazwa kolumny w insert różni się od @Column(name)
Table "…" not found klasa bez @Entity albo poza pakietem pl.wsb.<projekt>; inna nazwa w @Table(name)
NULL not allowed for column "…" kolumna z nullable = false pominięta w insert
Unique index or primary key violation dwa wiersze z tą samą wartością kolumny unique (np. numer stolika, nazwa pozycji menu)
No default constructor for entity brak konstruktora protected <Klasa>() {}
Port 8080 was already in use poprzednie uruchomienie wciąż działa: czerwony kwadrat w oknie Run

Błąd w data.sql zatrzymuje start aplikacji, więc czerwone są też R1.02 i R2.03. Czytajcie log od pierwszej linii z Caused by: tam jest nazwa tabeli i kolumny.

ZadanieG · Reguły, commit, pokazanie przebiegu

  1. Reguły lokalnie: panel Maven (prawa krawędź okna) → Lifecycle → dwuklik na verify. W oknie Run przy każdej regule R2.xx jest zielony albo czerwony znak, a przy czerwonej opis, co poprawić. Poprawiacie, aż LAB 01 i LAB 02 są zielone. Zestaw „LAB 02 · na ocenę 5” (R2.06–R2.07) jest potrzebny tylko na ocenę 5.
  2. Ostatnie zmiany: Commit z opisem (np. „Poprawki po regułach LAB 02”), Push. Na GitHubie zakładka Actions → przebieg „Testy i reguły” ma dwa etapy: Ocena 4 · reguły obowiązkowe (musi być zielony) i Ocena 5 · warunki dodatkowe (uruchamia się po zielonym etapie „Ocena 4”). Przy czerwonym etapie w Summary jest lista reguł do poprawy.
  3. Wizytówka: w static/index.html dopiszcie do listy zmian, co powstało na LAB 02 (nazwy tabel), potem Commit i Push. Od tego zaczniecie prezentację na kolejnych zajęciach.
  4. Pokazanie przebiegu (obowiązkowe): gdy wszystkie zmiany są na GitHubie, pokażcie prowadzącemu w zakładce Actions przebieg „Testy i reguły” dla ostatniego commita na main: oba etapy i Summary. Jeśli przebiegu nie ma albo dotyczy starszego commita, uruchomcie go ręcznie: Actions → Testy i reguły → Run workflow → gałąź main, w polu „Numer laboratorium” wpiszcie 2 → Run workflow.
  5. Tag lab-2 (opcjonalnie): zaznacza wersję do oceny. Okno Git → zakładka Log → prawy przycisk na ostatnim commicie → New Tag… → nazwa lab-2, potem Git → Push z zaznaczonym Push Tags. Tag sam uruchamia przebieg z regułami LAB 02.
